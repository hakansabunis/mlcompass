🔧 Feature engineering
  • Latitude + Longitude → Derive distance-to-coast and distance to major 
metros (LA, SF, San Diego, San Jose), KMeans cluster IDs, and/or rotated 
coordinates (e.g. 45-degree rotation) instead of using raw lat/lon alone.
     These two geo columns have no missing values and near-symmetric 
distributions (Latitude 32.54-41.95, Longitude -124.35 to -114.31), and housing
prices in California depend far more on proximity to coast/cities than on raw 
degrees.
  • MedInc → Add log(MedInc), percentile rank, and interactions with the geo 
features (e.g. MedInc x distance-to-coast).
     MedInc is right-skewed (mean 3.87 vs median 3.53, max 15.0, 681 IQR 
outliers) and is typically the dominant single predictor of price, so 
monotone/rank transforms and location interactions are high-value.
  • AveRooms + AveBedrms → Create AveBedrms/AveRooms ratio, AveRooms minus 
AveBedrms, and log-transformed versions; winsorize both at ~1st/99th 
percentile.
     Both are extreme-tailed (AveRooms max 141.9 vs median 5.23; AveBedrms max 
34.07 vs median 1.05) and highly collinear, so ratios and robust transforms 
carry more signal than the raw pair.
  • AveOccup → Use log1p(AveOccup) or a rank transform, and optionally 
cap/winsorize; consider a flag for extreme occupancy.
     AveOccup has the worst tail in the dataset (max 1243.3 vs median 2.82, std
10.39 versus a mean of 3.07), so raw values will dominate distance-based and 
linear fits.
  • Population → Add log(Population) and a derived household count = Population
/ AveOccup, plus population density proxies.
     Population is heavily right-skewed (max 35682 vs median 1166) and, 
combined with AveOccup, lets you reconstruct approximate district size and 
total-rooms totals.
  • Population + AveRooms + AveOccup → Cross-column: total_rooms = AveRooms * 
(Population / AveOccup) and rooms_per_person = AveRooms / AveOccup.
     AveRooms, AveOccup and Population are district-level averages, so explicit
count reconstructions expose absolute-scale effects that the raw averages hide.
  • HouseAge → Bin into decade buckets or add HouseAge x geo interactions 
rather than treating it as purely linear; keep the raw value for tree models.
     HouseAge spans 1-52 with no outliers (IQR/z-score counts both 0) and is 
symmetric (mean 28.6, median 29), so its value is likely interaction-driven 
rather than linear in price.

⚠ Pitfalls
  • Target is piled up at its maximum: 965 rows (4.7%) sit at exactly 1.79176, 
indicating a censored or capped price measurement rather than a true mode.
     → Treat as censored regression (Tobit) or fit a two-stage model: a 
classifier for 'at cap' plus a regressor on uncapped rows. At minimum, 
winsorize, avoid metrics that are dominated by cap errors, and report hold-out 
error separately for rows near 1.79176 so the systematic bias is visible.
  • Heavy-tailed outliers in AveOccup (max 1243.3), AveRooms (max 141.9), 
AveBedrms (max 34.1) and Population (max 35682).
     → Winsorize at 1st/99th percentile, use log1p/rank transforms, and scale 
with RobustScaler or quantile transformer before any linear or distance-based 
model.
  • Rows are census districts, so AveRooms/AveBedrms/AveOccup/Population are 
aggregate averages, not household-level values (measurement error / ecological 
fallacy).
     → Interpret coefficients as district-level; consider population-weighted 
fitting or adding reconstructed counts (total_rooms, households) as features 
rather than relying on averages alone.
  • Spatial autocorrelation and geographic leakage risk if you build 
location-based encodings or use random KNN features over Latitude/Longitude.
     → Use out-of-fold/KFold target encoding for any geo-derived feature, and 
consider GroupKFold by geographic cluster so nearby districts do not leak 
between train and validation.
  • Possible duplicate district records (a known characteristic of this dataset
family) and no explicit ID column.
     → De-duplicate on the full feature set (or on rounded lat/lon plus 
Population) before splitting, and verify the row count after de-duplication.
  • Small feature count (8 predictors, 20640 rows) makes it easy to over-fit 
via aggressive feature explosion or deep trees.
     → Use k-fold cross-validation, keep tree depth/regularization tuned, and 
check permutation importance stability across folds rather than trusting a 
single train/test split.
